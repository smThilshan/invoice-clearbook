# Key Decisions

Settled choices. Don't re-argue them in code; change them here first if needed.

| # | Decision | Why | Revisit when |
|---|---|---|---|
| 1 | Everything on Missan's local servers, including OCR and the model; no cloud, no third-party LLM APIs | Client financial data must not leave Missan's servers | Never, for client data |
| 2 | **Qwen3-VL-4B-Instruct** for the whole system, dev through production; PaddleOCR alongside. Exact model, never a default tag: dev = Ollama `qwen3-vl:4b-instruct` (plain `qwen3-vl:4b` is the **Thinking** variant: same 3.34 GB, much slower answers). Tested weights: `16b83be68214` (one 3.30 GB file, pulled 2026-10-14); the registry has since repackaged the same tag as `3a859c4dca68` + projector `70ac570fd36b`, so a tag alone is not a pin. Prod = vLLM with `Qwen/Qwen3-VL-4B-Instruct` at a fixed revision. A model change is deliberate and re-tested (smoke + evaluation), never an accidental re-pull | Testing done; small enough for dev Mac and a modest GPU; dev and prod results stay close | Fine-tuned adapter can't reach accuracy targets |
| 3 | Ollama (native) on dev, vLLM on prod, behind one `ExtractionClient` | Fast local dev; production throughput; switch by config | — |
| 4 | ~~Typed date folders as capture; folder declares, system verifies~~ Superseded by 25: per-restaurant folders on the shared drive, user picks the folder | Accountant already knows the type; free labels | Email capture needed |
| 5 | Review Workbench in our system; Approve posts to the accounting system | One place for all invoice work; only verified data in the accounting system; exact corrections | Missan insists on working only in Xero (fallback: post drafts) |
| 6 | Xero adapter posts as `SUBMITTED` in MVP and pilot, `AUTHORISED` by rule later | Extra gate while trust is built | Accuracy proven in pilot |
| 7 | Outbox + idempotent, resumable posting | No lost approvals, no double posting | — |
| 8 | Rule-based validation, never LLM-as-judge | Predictable, explainable, testable, auditable | — |
| 9 | Python backend (FastAPI, Celery, Postgres) | One language and one schema with the AI stack | Team standard changes |
| 10 | Post data only to the accounting system, no attachment; Missan's folders are the official archive | Simple, cheap, reliable | Finance requires attachments in Xero |
| 11 | Canonical invoice model; accounting-system logic only in an adapter (extended by 20) | Other accounting systems later without rebuild | Second accounting system needed |
| 12 | Fine-tune only on evidence, LoRA per client | Cheap fixes first; reversible adapters | Consistent error patterns |
| 13 | Monorepo: `backend/` + `workbench/` + `docs/` + `infra/` | One place, shared docs, simple for one engineer + Claude Code | Team grows |
| 14 | MVP in 3 weeks: functional first (Phases 1–5), non-functional later | Deliver working value fast; harden after | — |
| 15 | MVP storage = local filesystem behind `Storage` interface; MinIO later | Fewer moving parts now; no rewrite later | Phase 9 |
| 16 | MVP document types: bills, supplier credit notes, receipts | Covers the bulk of purchase-side work | Phase 11 |
| 17 | Only `document_type` (and line `amount`) required in the schema; "required to post" is a validation rule per type. Bill / credit note: number, date, total, vendor, currency missing → Error. Receipt: number missing → Warning, the rest → Error. Number null but a label like "Invoice No" / "رقم الفاتورة" in the text → flagged as likely missed. Accountant can mark "no number on document" (audited); a number is never generated | A field the model can't find must reach review flagged, not fail extraction; null over invented | Real samples (end-to-end run, Phase 5) show a different pattern |
| 18 | Business key = client + vendor + document type + key, where key is `N:<normalized number>` or, without a number, `F:<invoice date>\|<total>`. Partial unique index ignoring REJECTED, DUPLICATE, FAILED, VOIDED | Receipts often have no number but still need duplicate protection; a rejected document must not block its re-run | False positives on identical same-day receipts become a problem |
| 19 | "Only APPROVED → POSTING" enforced in the DB by a `BEFORE UPDATE OF status` trigger guarding that one edge; the full transition table lives only in `domain/state_machine.py` | DB safety net without two copies of the state machine drifting apart | — |
| 20 | The app runs standalone; accounting systems are optional adapters behind one `AccountingSystem` port, one per client. `manual` adapter (CSV master data in, export file out) needs no connection; Xero is the first API adapter (Phase 5); others (e.g. Zoho Books) only when a client needs them. Master data in neutral tables (`ledger_accounts`, `tax_rates`, `contacts`) with `provider` + `external_id` | Not locked to one vendor; the product works before any connection exists; a new system is one adapter, not a rebuild | A client needs a capability the port can't express |
| 21 | The model gets a flat JSON schema generated from `Invoice` (`pipeline/model_schema.py`): plain types, inline enums, all fields required, dates as printed text (decision 28; was `format: date`), no `anyOf`/`pattern`/`$ref`/defaults. Its answer is validated with the strict `Invoice` | Smoke test 1.7: Pydantic's validation schema as a decoding grammar made Qwen3-VL-4B return null for every field; Ollama ignores `pattern` but enforces `format: date` | Model or server changes; required fields cause invented values (watch `original_invoice_ref` on bills) |
| 22 | OCR = PaddleOCR 3.0.2 on PaddlePaddle 3.0.0 (Mar 2025), pinned; PP-OCRv5 mobile models on CPU (server models optional on GPU), behind an `OcrEngine` port (`adapters/ocr/`). Newer PaddlePaddle has no Intel-Mac build. Workarounds: models in `data/models/paddlex` + `HF_HUB_OFFLINE` once present; local font (stops a download from Baidu's cloud at import); langchain pinned <0.4; setuptools added. Known downside: PaddleX installs and loads OpenAI/LangChain client code (never called); `tests/test_dependency_guard.py` fails the build if our code imports it | Official PaddleOCR as planned, chosen over RapidOCR (same PP-OCR models via ONNX Runtime, no LLM-client packages); mobile models ~12x faster than server on CPU with the same result on test pages; real samples: mean confidence 0.92-0.98 | Dev moves to an M-series Mac or PaddleOCR drops the LLM extras; otherwise switch the `OcrEngine` adapter to RapidOCR |
| 23 | Currency is cross-checked, never corrected: the model extracts a 3-letter code; a rule compares it with markers printed on the page and only warns. Certain markers: ISO codes, Dh/Dhs/dirham, Arabic abbreviations, and the official signs U+20C3 UAE DIRHAM SIGN, U+20C1 SAUDI RIYAL SIGN, U+20C4 OMANI RIAL SIGN (Unicode 18.0, Sep 2026; dirham sign unveiled by CBUAE 27 Mar 2025, a D with two bars). Hints only: `$` (usually USD) and a standalone D / D-with-stroke / Eth before an amount (OCR reading of the dirham sign). Non-AED = warning (exchange rate); zero VAT from a foreign or unregistered supplier = warning (possible reverse charge), not an error. Prompt `extract-v2` tells the model what the dirham sign means | The sign is newer than most model and OCR training data and pre-Unicode-18 fonts map it to arbitrary characters; amounts parse regardless of the symbol | Real samples with the sign show a different OCR reading |
| 24 | Grounding: number, document date, subtotal, VAT, total and supplier TRN must be found in the page text after normalization (error); due date (warning, often printed as terms); zero VAT need not be printed. OCR pages only: letters OCR confuses with digits (O, l/I, S, B…) next to digits also count as digits; the exact PDF text layer gets no tolerance. A value the accountant confirms or types in review is human-verified and no longer grounded (Phase 4) | The model, seeing the image, may correctly fix an OCR misread; the accountant is the final judge and cannot fix the OCR itself | Tolerance lets wrong values through on real samples |
| 25 | Each restaurant is a client with its own folder on Missan's shared drive, kept the way the accountants already organise it (e.g. month folder, day folders inside). The user picks the restaurant and a folder; the run includes its sub-folders; the selected path must stay inside that client's folder. Documents are purchase-side by default; no typed Purchase/Sales/Unsorted folders. The folder date is read from the folder name when it holds one (and confirmed on the Run screen); otherwise the period check is skipped. Replaces decision 4's typed date folders (task 3.9) | Follow Missan's existing practice instead of forcing a new sorting step; each restaurant has its own chart of accounts and suppliers (`client_id` everywhere) | Sales-side documents come into scope (Phase 11) |
| 26 | Login and roles are deferred until after pilot testing (start of Phase 6). Until then the API and Workbench run on one machine and the API listens on 127.0.0.1 only; nothing may expose it on the network. All accountants may work on all restaurants (users belong to Missan, no per-restaurant restriction). When built: Argon2 password hashes, JWT with expiry, roles reviewer / approver / admin, approve = approver only | Use and test the workflow first; login is not needed while only one machine can reach the system | Anyone needs the Workbench from another computer, or real daily use starts |
| 27 | Workbench UI: shadcn/ui (component source copied into the repo; Radix UI behaviour + Tailwind CSS) | Fits the chosen stack (React Hook Form for the review form, TanStack for data and tables); the code is ours, so no forced upgrades; accessible keyboard behaviour for accountants | — |
| 28 | The model copies dates exactly as printed (plain text); our own parser converts them, day-first as in the UAE (`4/5/2026` = 4 May 2026); text with no date becomes null and is flagged. New checks: a document date before 2000 is an error, one more than 2 years old a warning; a supplier TRN equal to the customer's TRN is an error | First real run (EXP-002, ROAST May): forced to `format: date` (YYYY-MM-DD), the model copied `4/5/2026` digit by digit into the year (`4520-05-04`) on all 7 documents; it read day and month right. Converting is deterministic work, not the model's (rule 7) | A supplier prints month-first dates (US style): add a per-supplier date order |
| 29 | Our own TRN finder (`verify/trn_finder.py`) reads the TRNs printed next to their labels (TRN, VAT/Tax Registration No, TIN, الرقم الضريبي; small scanner misspellings allowed; exactly 15 digits; excise/licence/phone numbers never) and decides whose by position (highest label on page 1 = supplier, even if unreadable) and customer labels. Grounding compares the model's TRNs with it: different or missed = error for the supplier, warning for the customer, with the printed value as a `suggestion` the accountant can accept (never applied automatically). A PDF page that one picture covers (≥ 90%) is a scan: its text layer came from the scanner's OCR and is marked `ocr`, so OCR misreads (S for 5) are tolerated | First real run (EXP-002): suppliers print "VAT REGISTRATION NO" next to a 10-digit excise number; the model put the customer's TRN in the supplier field on 3 of 7 documents and misread digits; the ROAST PDFs are scans whose scanner text has OCR errors | Suppliers whose header shows several TRNs (group companies); learn each supplier's TRN once approved (task 4.8) |
| 30 | Photo quality (`pipeline/page_quality.py`): every page that is a picture (photo, or a scanned PDF page) gets a sharpness, brightness and uneven-light measure in the Read step (~25 ms per page, OpenCV). A blurry, dark or shadowed page is a warning in review (values may be misread; ask for a clearer copy), never a block. Before our own OCR, shadowed or dark pages get their light evened out; good pages are never changed, and the model and viewer always get the original image. Thresholds from EXP-002 pages (sharp 4,700-6,600, soft thermal receipt 1,354, unreadable photo 166) | Most purchase documents are phone photos saved as PDF. Measuring is cheap and tells the accountant why values may be wrong; heavier fixes (perspective unwarping, orientation model) only if the scores show they are needed | Thresholds on 20+ real photos; many angled or crumpled photos (then PaddleOCR's unwarping); a photo guide for the restaurants |
| 31 | (a) Model extraction has its own Celery queue, `extract`; workers take queues in a fixed order (`pipeline`, `posting`, `extract`; Redis `queue_order_strategy: priority`), so a quick step (read, verify, posting) never waits behind queued extractions and each document reaches review as soon as its extraction is done. (b) Folder names without a year ("May", "May/May 1", "May/1", "1 May") take the most recent such date up to the business day; a year on a parent folder wins; month names must be whole names or abbreviations ("Marketing" is not March) | EXP-002: with one first-in-first-out queue all 7 documents reached review only after the last extraction (25 min); ROAST's folders are "May/May 1", so no folder date and no period check | Production with a GPU model server: give `extract` its own worker pool sized to it; a folder for a period more than a year back without a year in its name |
| 32 | Review screen (task 4.5): the page viewer shows the page pictures the Read step already made (`/documents/{id}/pages/{n}/image`), not the PDF itself, so react-pdf (in the original stack) is not used. The form uses React Hook Form (field array for lines, change tracking). Amounts stay text in the browser; live totals use exact whole-number arithmetic (`lib/money.ts`), never JavaScript floats | One viewer for PDFs, scans and phone photos alike; no PDF.js in the browser; the same pictures the model saw | Need for selectable PDF text or vector zoom in the viewer |
| 33 | Step timings (task 4.9): each pipeline step saves its own work time (`work_ms`; Verify also `coding_ms`, the model's part) in the details of the audit row it already writes; no new table. The audit row's `created_at` is the transaction start, i.e. when the step began, so waiting = gap between one step's end and the next one's start (queued behind other files, or model retries). Shown per file on the run page and as one line on the review screen; documents from before 4.9 show only the model time | Accountants and we need to see where the minutes go (model vs waiting in line) to judge speed honestly; a timer costs nothing, and the audit log is already the step history | A step stops running in a single transaction, or timings are needed outside the Workbench (then `make run-report` for EXP reports) |
| 34 | VAT type (`amount_type`, task 4.10): set from the amounts right after extraction, replacing the model's guess. The prompt is unchanged (extract-v4) and still asks for it, because on this 4B model any wording change shifted other fields (EXP-004: removing the line cost a TRN digit; dropping `evidence` + compact JSON flipped this field and once never finished). The rule (±0.01): VAT > 0 and lines + VAT = total → EXCLUSIVE; VAT > 0 and lines = total → INCLUSIVE; no VAT and lines = total → NO_TAX; anything else → empty, the accountant chooses (never guessed). This is a value worked out from extracted amounts, like a sum; the model's guess stays in the raw answer, and a type that contradicts the amounts is always flagged (rule 8 holds). The check `vat_type` flags a type that contradicts the amounts (warning, with the amounts' type as a one-click suggestion; replaces the "lines do not add up" warning in that case) and a missing type on a document with VAT (error: posting needs it) | EXP-004: the model read the amounts right but judged the type from headings and got it wrong even with v4 (a dairy supplier's "INCL EXCISE" and "NET INVOICE AMOUNT" columns); the type also flipped when unrelated prompt wording changed. A wrong type posts the wrong VAT to Xero, so it must not rest on a judgement call the arithmetic answers exactly | Documents whose lines legitimately do not add up (discount or delivery lines outside the lines) are often left empty: then add discount/charge handling, or ask the model again only for those |
| 35 | Any client, any folder (task 4.12), replacing the folder rule of decision 25. Clients are any business (not only restaurants) and are created on the Run screen from a name; their own folder is optional. A run may use any folder inside the **allowed places**: the client's own folder, plus `FOLDER_PLACES` (default: the home folder and `/Volumes`, the shared drives). Each run stores its place (`runs.root_path`); its `folder` and the documents' `source_path` are relative to it (runs from before have none and use the client's folder). Paths cannot leave a place (no `..`, no absolute paths, links pointing out refused), and the top of this Mac or of the shared drives cannot be run whole. Files are read in place, never copied or changed | The user must pick local or shared folders and create clients without the terminal, and Missan serves more than restaurants. Limiting reads to configured places keeps system folders out of reach; the API still listens on localhost only, and login comes before it listens anywhere else (Phase 6) | Users work from other computers than the one running the app (then a browser upload of a chosen folder), or the places need per-user limits (with login) |
| 36 | Charges outside the lines (task 4.13): the `Invoice` schema stays lines + subtotal + VAT + total. When the total does not add up, deterministic code looks for printed charges that explain the gap **exactly** (±0.01) and **uniquely**: first every labelled amount printed between the subtotal and the total line (any label, so unseen charges are found), then labelled amounts with a hint word from settings. Discount words make an amount negative; an amount printed without a decimal point ("141") is also tried as money ("1.41"). When the stored page text cannot explain it and the page is a picture, our own OCR reads the page once in the verify step (best effort, a few seconds, only for these documents) and is kept for re-checks. The result is one error naming the charges, and the Workbench adds them as lines (and to the subtotal) on one click; the model and prompt are unchanged | Receipts (delivery apps, supermarkets) put fees outside the item lines; the strict totals rule flagged correct documents, and posting needs those fees as lines with an account. Prompt or schema changes moved other fields in EXP-004; arithmetic over printed amounts cannot invent a charge, and two possible explanations offer nothing (flag, never guess) | Charges often unexplained (see the corrections), or the same supplier's fee needs its account suggested (remember supplier + charge → account), or the model is asked for charges (tested before/after) |
| 37 | Live progress (task 4.14): each worker step marks the document `working_step` + `working_since` in its own short transaction just before it starts; the mark only counts while the status is still the one that step works on (so it never needs clearing). The run page derives each file's step, its place in line for the AI (documents waiting, oldest first, all clients: one model) and the time left from the median work time of the last 20 processed files. Polling every 3 s stays (no push yet) | The run page said "Read" for the whole four minutes the model worked, which looked stuck; a step's end was recorded, its start was not | Many runs at once or several workers (then server push, and per-worker lines) |
